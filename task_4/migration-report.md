
## 1. Анализ ситуации

### Компоненты, затрагиваемые миграцией

| Компонент | Текущее состояние | Целевое состояние |
|---|---|---|
| Учёт пациентов и записи | Excel на сетевой шаре | Сервис пациентов и сервис записи, PostgreSQL |
| Медицинские карты | Сканы и PDF в каталогах | Сервис медицинских карт, объектное хранилище |
| Учёт анализов | `RegistryByDate.xlsx` | Интеграция с лабораторией по API |
| Платежи | ККМ, 1С:Бухгалтерия в файловом режиме, теневой Excel | Платёжный сервис, единый источник данных |
| Учёт ТМЦ | 1С:Торговля и склад в файловом режиме | Сервис склада |
| Каналы обслуживания | Обращение на ресепшен | Портал пациента и портал сотрудников |
| Обмен между системами | OLE и TCP/IP внутри одной машины | Сетевые вызовы и события |
| Инфраструктура | Один физический сервер в здании офиса | Кластер с резервированием |

### Условия перехода

Рост объёма данных в пять раз, открытие филиалов, активный наём. IT-отдел - три человека.

### Ключевое свойство перехода

Меняется способ взаимодействия компонентов. В монолите вызов метода занимает доли микросекунды и не может завершиться сетевой ошибкой. В микросервисах тот же вызов идёт по сети, требует сериализации и шифрования и может не завершиться вообще. Большинство узких мест вытекает из этого различия.

## 2. Категории и выявленные проблемы

### Инфраструктура

| Проблема | Влияние на производительность |
|---|---|
| Единственный сервер в здании офиса | Масштабировать нечего, отказ узла останавливает работу клиники |
| Плоская сеть без сегментации | Межсервисный трафик конкурирует с пользовательским |
| Нет запаса мощности под рост данных ×5 | Расчёт нагрузки не проводился, объём хранилища не спланирован |
| Отсутствует автомасштабирование | Утренний пик записи обслуживается теми же ресурсами, что и ночь |
| Ресурсы под Kubernetes не рассчитаны | Оркестратор потребляет 15–25 % узла, прикладным сервисам остаётся меньше, чем было у монолита |

### Данные и хранилища

| Проблема | Влияние на производительность |
|---|---|
| Распределённые транзакции между сервисами | Запись на приём затрагивает два сервиса, требуется сага, время операции растёт кратно |
| Общая БД при разделённом коде | Сервисы формально независимы, фактически конкурируют за блокировки и пул соединений |
| Миграция из Excel без схемы и валидации | Дубликаты, некорректные даты, разные форматы ФИО останавливают перенос или создают неконсистентные данные |
| Нет индексов под новую модель | Запросы к сотням тысяч записей дают полное сканирование таблицы |
| Согласованность в конечном счёте | Отчёт в момент рассинхронизации показывает расхождение, воспринимается как ошибка |

### Программное обеспечение

| Проблема | Влияние на производительность |
|---|---|
| Неверные границы сервисов | Один сценарий проходит через пять сервисов, каждая граница добавляет задержку |
| Синхронные цепочки вызовов | Время равно сумме, доступность - произведению: четыре сервиса по 99 % дают 96 % |
| Проблема N+1 | Список из тридцати записей превращается в тридцать один сетевой вызов |
| Нет кеширования справочников | Услуги и расписание запрашиваются из БД при каждой операции |
| Бизнес-логика 1С не воспроизведена | Правила расчёта не задокументированы, расхождения обнаружатся на закрытии периода |

### Интеграции и коммуникации

| Проблема | Влияние на производительность |
|---|---|
| Обмен по OLE не переносится в сеть | Механизм работает внутри одной машины Windows, требуется полная переработка |
| ККМ требует синхронного ответа | Медленный платёжный сервис создаёт физическую очередь в кассу |
| Нет таймаутов, повторов, предохранителей | Зависший сервис блокирует потоки вызывающего, возникает каскадный отказ |
| Сетевые задержки вместо вызовов в памяти | Разница в тысячи раз незаметна при одном вызове и критична при сотне на операцию |
| Накладные расходы шифрования каналов | Установление сессии TLS без переиспользования соединений заметно в задержке |

### Процессы

| Проблема | Влияние на производительность |
|---|---|
| Одномоментный переход | При отказе останавливается вся клиника, приём пациентов приостановить нельзя |
| Нет нагрузочного тестирования | Профиль нагрузки после запуска портала неизвестен, узкое место проявится на боевой нагрузке |
| Отсутствует мониторинг и трассировка | В распределённой системе без сквозной трассировки невозможно установить, где потеряно время |
| Нет плана отката | При деградации вернуться к прежнему процессу нечем |
| Параллельный ручной учёт | Нагрузка на сотрудников удваивается, данные расходятся между контурами |

### Персонал

| Проблема | Влияние на производительность |
|---|---|
| IT-отдел из трёх человек | Недостаточно для одновременной разработки, эксплуатации и миграции |
| Нет опыта распределённых систем | Ошибки конфигурации проявляются только под нагрузкой |
| Сотрудники не обучены | Скорость работы упадёт в первые недели независимо от качества системы |
| Знание бизнес-логики не задокументировано | Часть правил будет утеряна при переносе |
| Нет дежурства и регламента реагирования | Время восстановления после отказа не ограничено |

## 3. Рекомендации по приоритетам

### Критический приоритет - до начала миграции

| № | Мера | Устраняет |
|---|---|---|
| 1 | Поэтапная миграция по шаблону «удушающий фасад»: функции перехватываются по одной, старая система работает параллельно | Одномоментный переход, отсутствие отката |
| 2 | Расчёт нагрузки и планирование мощностей | Нет запаса мощности |
| 3 | Резервный контур инфраструктуры, бэкапы за пределами здания | Единая точка отказа |
| 4 | Границы сервисов по бизнес-возможностям, а не по техническим слоям | Неверная декомпозиция |
| 5 | Отдельная база данных на сервис, запрет общей БД | Скрытая связность через хранилище |
| 6 | Очистка и валидация данных, пробный прогон миграции на копии | Миграция из Excel без схемы |
