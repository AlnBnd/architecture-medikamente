Утечка означает раскрытие сведений о здоровье конкретного человека, репутационный ущерб клинике и иски пациентов | Шифрование на уровне поля AES-256-GCM или ГОСТ Р 34.12-2015, ключ из HashiCorp Vault; доступ по ABAC через OPA «лечащий врач - этот пациент»; MFA для медицинских ролей; аудит каждого чтения в ELK |

| **Связка пациент - специалист** | `RESTRICTED`, at rest, высокий | Факт записи к профильному врачу сам по себе раскрывает врачебную тайну даже без диагноза | Псевдонимизация: `patient_id` вместо ФИО в журналах; маскирование ФИО в списках ресепшена |

| **Сканы паспорта и договора** | `CONFIDENTIAL`, at rest, высокий | Позволяют совершить мошеннические действия от имени пациента | Шифрование объектов; отдельное хранилище документов, изолированное от медицинского домена; автоудаление по истечении срока |

## 2. Шифрование по состояниям данных

Три состояния требуют разных механизмов. Защита одного не заменяет защиту другого.

### At rest - при хранении

| Слой | Механизм | Что защищает |
|---|---|---|
| Диск и носитель | Полнодисковое шифрование, самошифрующиеся диски | Кражу физического носителя, вынос диска из здания |
| База данных | Прозрачное шифрование TDE | Доступ к файлам БД в обход СУБД |
| Отдельные поля | Шифрование на уровне приложения перед записью | Доступ администратора БД к содержимому диагнозов |
| Объектное хранилище | SSE-KMS, ключ на bucket | Утечку объектов документов |
| Резервные копии | Шифрование бэкапа отдельным ключом | Утечку бэкапа, вынесенного за пределы площадки |

Ключевой момент: прозрачное шифрование БД защищает от доступа к файлу, но не от того, у кого есть учётная запись СУБД. Поэтому для полей уровня `RESTRICTED` применяется шифрование на уровне приложения - в БД попадает шифротекст, ключ администратору БД недоступен.

### In transit - при передаче

| Участок | Механизм |
|---|---|
| Клиент - система | TLS 1.3, HSTS, закрепление сертификата в мобильном приложении |
| Между сервисами | mTLS, взаимная аутентификация по сертификату |
| Система - лаборатория | mTLS, подпись сообщений, контракт API вместо файлов |
| Система - эквайер и ОФД | TLS, требования платёжного и фискального протоколов |
| Между площадками филиалов | Криптошлюз с сертификацией ФСБ, ГОСТ-каналы |
| Резервное копирование | Шифрованный канал до хранилища бэкапов |

При передаче персональных данных внутри РФ применяется криптография по ГОСТ Р 34.12-2015 и ГОСТ Р 34.10-2012 с сертифицированными средствами.

### In use - при обработке

Наименее очевидное и часто пропускаемое состояние.

| Угроза | Мера |
|---|---|
| Оператор видит больше, чем нужно для задачи | Маскирование на уровне выдачи по тегу поля |
| ПДн попадают в логи и трассировку | Маскирующий фильтр в логгере на этапе записи |
| Данные видны на экране постороннему | Автоблокировка сессии, водяной знак с идентификатором пользователя |
| Выгрузка в файл и вынос данных | Запрет экспорта для `RESTRICTED`, DLP на исходящих |
| Данные в памяти процесса | Ограничение времени жизни в памяти, запрет дампов памяти в проде |

## 3. Автоматизированный контроль

Контроль должен работать без участия человека, иначе он не работает.

### На этапе разработки

| Средство | Что проверяет | Реакция |
|---|---|---|
| Линтер тегов данных | Каждое поле схемы размечено тегом | Сборка падает |
| Conftest и OPA | Поле `PII.SPECIAL` не уходит наружу без маскирования | Сборка падает |
| SAST | Уязвимости в коде, захардкоженные секреты | Блокировка слияния |
| SCA | Уязвимости в зависимостях | Блокировка при критических |
| Gitleaks | Секреты в репозитории | Блокировка коммита |

### В рабочем режиме

| Средство | Что контролирует | Реакция |
|---|---|---|
| SIEM | Корреляция событий доступа | Инцидент и оповещение |
| Правила детектирования аномалий | Массовое чтение карт, доступ вне рабочего времени, обращение к чужим пациентам | Оповещение офицеру по защите данных |
| DLP | Исходящий трафик и почта с тегом `RESTRICTED` | Блокировка передачи |
| Мониторинг доступности | Состояние сервисов и хранилищ | Оповещение дежурному |
| Контроль целостности | Изменение критичных файлов и конфигураций | Инцидент |
| Сканер уязвимостей | Периодическая проверка инфраструктуры | Задача на устранение |
| Автоудаление по сроку | Данные с истёкшим `retention` | Удаление и запись в журнал |
| Проверка k-анонимности | Наборы перед выгрузкой в аналитику | Блокировка конвейера |

### Периодические процедуры

Пересмотр прав доступа раз в квартал, проверка восстановления из бэкапа раз в квартал, ротация ключей по расписанию Vault, тест на проникновение раз в год, актуализация модели угроз при изменении архитектуры.
